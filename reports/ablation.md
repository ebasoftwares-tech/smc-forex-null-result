## What this report does NOT establish

**Every delta below is measured in-sample, on a baseline whose own expectancy
is not distinguishable from zero** (D-027: -0.19 R over 102 trades). A row that
moves the delta is moving a number that has not been shown to be positive, so
'better' here means 'less bad', and no row licenses changing a default on the
strength of its number alone.

Section 6.5's rule is the one followed: *a component whose delta CI spans zero
is reported as "no measurable effect" and its default stands* -- not kept
because it looked slightly positive, not removed because it looked slightly
negative. Every row is additionally corrected across the matrix (section 5.6),
because 34 tries on one dataset is 34 chances to find something.

Two limits worth stating before any row is read: this is the **in-sample**
split, and only four of the ten symbols can carry a sized trade (D-026), so
every delta is measured on those four.

What the run **does** establish is structural and holds whatever the data: which of
section 6.5's nineteen components can be toggled at all, and which of the shipped
defaults are live rather than inert. That is the report's most durable output.

### The 3 components that exist nowhere in the codebase

**This is the first finding and it is not about the data.** Section 6.5 names these
as ablation dimensions; none of them can be toggled because none of them is
implemented:

- **session filter** (`(none)`) -- No execution-side session filter exists. `SessionWindowConfig.role` is read only by `liquidity_session_names`, which picks liquidity SOURCES. No module gates an entry on the session it fires in.
- **killzone filter** (`(none)`) -- `role: killzone` is an accepted value and LONDON_KZ / NY_KZ are defined in `defaults.yaml` with `enabled: false`, but nothing reads them. Enabling them would only add two more session windows, not a filter.
- **tier -> confirmation-TF map (D-002)** (`liq.tier_confirmation_tf = {'3': 'H1'}`) -- **Section 6.5 names this one explicitly as 'the D-002 counterfactual'.** `liq.tier_confirmation_tf` is declared in the schema, documented as ABLATION, and read by no module: `analyse_sweeps` steps the H4 series for every tier by construction. Running it needs a per-tier confirmation timeframe in the liquidity and sweep engines, which does not exist.

The third is the one that matters most: section 6.5 calls `liq.tier_confirmation_tf`
**"the D-002 counterfactual"**, the alternative to the decision that shapes the
entire model (`STATE.md` §5: *"H4 confirmation for every liquidity tier ... this is
a session-to-session swing model, not the intraday London reversal the SMC source
material describes"*). The parameter is declared, documented as ABLATION, and read
by no module. **D-002 cannot currently be tested against its own alternative.**

## Why the paired/unpaired split is reported, not hidden

Median MDE: **0.0200 R paired**, **0.0321 R unpaired** -- a factor of 1.6.

A paired row runs two configurations over **one setup stream** and takes the
difference per setup, so what is bootstrapped is the variance of a *difference* and
most of the market noise cancels. An unpaired row rebuilds the Market, so the two
arms are different populations and every bit of that noise is back.

That is not a presentational detail. **An unpaired delta cannot separate "this
component changed outcomes" from "this component changed what we traded"** -- a
sweep filter that removes half the setups shifts expectancy simply by selecting a
different population, and reading that as the filter's value is how a filter that
only reduced sample size gets recorded as one that improved the edge. Every
`UNPAIRED` row above carries that caveat; the `n` column shows how far the
population moved.

## Findings

### 1. Five of section 6.5's nineteen components cannot be toggled

Two are blocked on Phases 2-4, which is expected and recorded. Three are **absent**:
session filter, killzone filter, and `liq.tier_confirmation_tf`. The last is the one
section 6.5 calls *"the D-002 counterfactual"*, and D-002 is the decision that makes
this a session-to-session swing model rather than an intraday one. It is declared in
the schema, marked ABLATION, and read by nothing.

### 2. `ob.definition` was hardcoded in the engine, and is inert even once fixed

`_pass_one` passed `definition=ObDefinition.A_LAST_OPPOSING` as a literal, so the
config field was ignored and the four SPEC 13.2 variants were unreachable end to
end. Fixed (D-017), and the four now produce visibly different results **under entry
model D**. At the shipped defaults they still change nothing, because entry model C
reads an FVG and stop model S1 reads the sweep extreme -- neither consumes an order
block. An ablation of the OB definition is only meaningful at entry D or SL S3.

### 3. A retracted finding: T2 was not blocked by a parameter (D-019)

**The previous version of this report was wrong here and the correction is worth
more than the original claim.** It reported `tp.min_target_rank = 2.0` as a fifth
default that cannot fire, on top of D-014's four, because T2 rejected every setup
with `NO_TARGET_AVAILABLE`. The rejection reason was read as the cause.

It was not the cause. **Two engine bugs were**, and neither is a parameter:

| | |
|---|---|
| 1 | `_pass_one` never passed `levels` or `ranks` to `evaluate`, so `select_target_level` filtered an **empty sequence**. `Market` did not even carry the liquidity book -- `build_market` kept `len(book.levels)` and discarded it |
| 2 | `_opposing_side` was **inverted**: it sent a long at SELL_SIDE liquidity, which `liquidity.Side` defines as the pool *below* price. SPEC 17.1's own worked example targets "nearest opposing liquidity **PDH**" for a BUY LIMIT, and a previous-day high is BUY_SIDE |

**The measurement that would have caught it took one line**: set `min_target_rank`
to 0 and see whether anything changes. Nothing did -- the same rejection on every
setup -- because the filter was never reached. *A rejection reason names the gate
that refused, not the reason it refused.*

Both are fixed. The book now reaches the gate as a **per-bar snapshot**, because the
finished book cannot be read causally at all: SPEC 8.8's merge rewrites a surviving
level's price, tier and strength in place, which is the trap D-009 §4 recorded for
swings and D-011 §3 for FVGs, arriving a third time.

With the gate able to see the book, T2's binding constraint is **SPEC 17.2's RR
gate**, not the rank filter: the nearest qualifying level is usually closer than
`min_rr` = 1.5. That is the gate working as designed.

**`tp.min_target_rank` was subsequently raised 2.0 -> 5.0 by
explicit instruction, and it was selected by its outcome on the SYNTHETIC fixture** -- the
basis §10.2 prohibits. See D-019 for the provenance and `PRE_REGISTRATION.md` §11
for the re-registration. No number below that depends on it should be read as
evidence that the value is right.

### 4. INERT is not "no measurable effect", and section 6.5's rule cannot tell them apart

6 variants changed the outcome of zero setups. Section 6.5's sentence
for a CI spanning zero -- *"no measurable effect, the default stands"* -- says the
component was tested and did not matter. For an inert row nothing was tested. Same
number, opposite conclusion. The time stop is the clearest case: **15, 30, 60 and
"off" are all identical**, because no trade in this sample lives long enough for any
horizon to bind. A reader given only "no measurable effect" would conclude the time
stop is decoration; what the data says is that it was never reached.

### 5. "One component at a time" is not achievable where components share objects

Section 6.5's method assumes a component can be toggled in isolation. Three of its
rows cannot be, because the default entry model consumes something another
component produces:

| Toggle | Coupled to | What happens |
|---|---|---|
| `disp.mode = bar` | `entry.model = C` | `leg` mode confirms displacement **by finding an FVG** (`require_fvg`), so model C always has one to enter on. `bar` mode (SPEC 10.3) produces none: **113 of 145 setups reject with `NO_FVG_AVAILABLE`** and the arm fills 2 trades. The row measures the entry model, not the displacement mode. |
| `disp.require_fvg = False` | `entry.model = C` | Same mechanism from the other side: it nearly doubles the setup count and fills the same number of trades. |
| `ob.definition = B/C/D` | `entry.model = C`, `sl.model = S1` | Neither default consumes an order block, so all three are INERT (finding 2). |

All three need a second axis to be read at all -- displacement at entry model A,
the OB definition at entry D or SL S3. **A one-at-a-time matrix cannot express
that**, and reporting these rows as though it could would attribute the entry
model's dependency to the component being toggled. This is the same shape as
D-016 §2, where two falsification controls could not run at the default entry
model either, and it is the second time the shipped default has turned out to be
the awkward one to measure against.
